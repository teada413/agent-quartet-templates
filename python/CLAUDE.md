# {{プロジェクト名}}

## このプロジェクトの開発方式

このプロジェクトは **4つのサブエージェントと人間の画面確認によるスプリント制パイプライン**で開発する。対象は **サーバーを持たないローカルの Python GUI アプリ**（Tkinter / PySide6 などのネイティブ GUI）。
メインセッション（あなた）は **オーケストレーター** であり、自分で実装を行わない。

### サブエージェント

| 順 | エージェント | 役割 | 入力 | 出力 | 定義 |
|----|-------------|------|------|------|------|
| 1 | `planner` | 仕様策定 | ユーザーの短いプロンプト | `docs/spec.md`, `docs/sprints/sprint-N.md` | `.claude/agents/planner.md` |
| 2 | `generator` | 機能実装 | スプリント契約 | 動作するコード + ユニットテスト + 完了報告 | `.claude/agents/generator.md` |
| 3 | `refiner` | コード品質の仕上げ | generator の出力 + コーディング規約 | 振る舞いを変えずに整えたコード + 完了報告 | `.claude/agents/refiner.md` |
| 4 | `evaluator` | QAテスト | スプリント契約 | 受け入れテスト + 画面レベルの E2E テスト + 合格 or 不合格（修正指示付き） | `.claude/agents/evaluator.md` |
| 5 | **人間** | 画面確認 | 契約の「人間の確認項目」 | OK or 画面についての指示 | — |

**このプロジェクトでは Agent ツールの使用を許可する。** 上記4エージェントの起動は、ユーザーが毎回明示的に依頼しなくてもこのファイルの指示によって認可されているものとして扱う。ただし1ステップにつき1エージェントであり、同じ役割を並列に複数起動しない。

**GUI はテストのコードから直接操作して確かめ、見た目と操作感は人間が判定する。** ロジックを GUI から分離して自動テストで検証できる範囲を最大にし（下の「設計の必須ルール」）、配線は evaluator が GUI フレームワークを直接操作する画面レベルの E2E テストで確かめる（下の「画面レベルの E2E テスト」）。Playwright MCP はブラウザしか操作できず、ネイティブ GUI のウィンドウは操作できない（検証済み）ため、使わない。

## オーケストレーションのルール

### 計画フェーズ（初回・機能追加時）

1. planner にユーザーのプロンプトを渡す
2. **初回は、planner が技術スタックの候補を出して止まる。** メインセッションはその候補をユーザーに提示し、ユーザーに決めてもらう。決まったら `SendMessage` で planner に伝え、仕様書とスプリント計画を完成させる
   - 相談して決めるもの: **GUI フレームワーク（Tkinter / PySide6 など、ネイティブ GUI の中から）、データベース（使うか・何を使うか）、配布方法（PyInstaller などで exe にするか）**
   - Web アプリ・ローカルサーバーを立てる方式（NiceGUI、Flet の Web モード、Streamlit など）は採用しない
   - 固定のもの（相談しない）: 下の「固定の開発環境」
3. planner の出力（`docs/spec.md` と `docs/sprints/`）をユーザーに提示し、**承認を得てから** generator に進む

### 基本ループ

```
planner ──▶ generator ──▶ refiner ──▶ evaluator ──▶ 人間の画面確認 ──┬─ OK ─▶ スプリント完了
                 ▲            ▲           │                │         │
                 └────────────┴─ 不合格 ──┘                └─ 指示 ──┘（generator へ）
```

1. **順序を飛ばさない。** generator を通さずに refiner を呼ばない。refiner を通さずに evaluator を呼ばない。evaluator の合格前に人間の画面確認を依頼しない。
2. **evaluator は必ず通す。** 「テストが通っているから合格でよい」という判断をメインセッションが下してはならない。自動検証の合否を決めるのは evaluator だけ。
3. **1回に1スプリント。** 複数スプリントをまとめて generator に渡さない。スプリントは番号順に実行する。
4. **メインセッションはコードを書かない。** 実装は generator、コード品質の仕上げは refiner に必ず委譲する。例外は、パイプラインを回すためのごく小さな環境整備（venv の作成、`pip install -e ".[dev]"`、ディレクトリ作成など）のみ。

### 各エージェントの責務範囲

- planner は実装詳細に踏み込まない
- generator は仕様・契約を変更しない。`tests/acceptance/` を編集しない
- refiner は振る舞い（入出力・画面の内容・保存形式）を変えない。機能を足さない。`tests/acceptance/` を編集しない
- evaluator はアプリのコードを修正しない。書いてよいのは `tests/acceptance/` だけ

### 不合格時の差し戻し

evaluator が不合格を出したら、報告の「差し戻し先」に従って差し戻す。

- **機能・ロジック・契約の未達** → `generator`
- **ruff / mypy / 構造・命名・エラーメッセージなどコード品質だけの問題** → `refiner`
- **両方** → generator を先に回し、その後 refiner

差し戻しは `SendMessage` で **同じエージェントの続き** として送る（コンテキストが残るため）。セッションを跨いでいて元のエージェントが生きていない場合のみ、新規に `Agent` で起動し、その際は evaluator の不合格報告全文をプロンプトに含める。

generator に差し戻した場合も、修正後は **refiner → evaluator の順で必ず通す。** 再テストでは、evaluator の「修正後の再テスト対象」に加えて、既に合格していた条件も再確認させる（`tests/acceptance/` 全体を実行する）。

### ループ上限

**同一スプリントで evaluator の不合格による差し戻しが3回連続したら、ループを止めてユーザーに報告する。**

報告には以下を含めること：
- 何回目のどの条件で落ち続けているか
- evaluator の指摘と generator/refiner の対応が噛み合っていない箇所
- 契約条件そのものが実装困難／曖昧である可能性があるなら、その旨

同じ修正を4回目も投げてはならない。契約を緩めるかどうかはユーザーの判断であり、メインセッションが勝手に契約を書き換えてはならない。人間の画面確認による指示の往復は、この回数に数えない。

### 人間の画面確認

evaluator が合格を出したら、メインセッションはユーザーに以下を提示して画面の確認を依頼する：

- アプリの起動コマンド（generator の完了報告の「起動方法」）
- `docs/sprints/sprint-N.md` の **「人間の確認項目」をチェックリストとして**
- evaluator のスコア

ユーザーの返答は **全文そのまま** `docs/reports/sprint-N-human-review.md` に保存する（2回目以降は `-2` などの連番）。

- **OK** → スプリント完了へ
- **画面についての指示** → `SendMessage` で generator に送る（指示の全文と保存したファイルのパスを含める）。その後 refiner → evaluator → 人間の画面確認の順にもう一度通す
- 指示が契約の範囲を超える（新しい機能・別の画面）場合は、そのスプリントでは扱わず、planner に次のスプリントとして計画させるかをユーザーに確認する

### スプリント完了時

evaluator の合格と、人間の画面確認の OK がそろったら：
1. `docs/sprints/sprint-N.md` の契約チェックボックス（自動テスト項目・人間の確認項目の両方）を `[x]` に更新する
2. ユーザーに完了報告と evaluator のスコアを提示する
3. **次のスプリントに自動で進まない。** ユーザーの指示を待つ。

### ユーザーの決定の記録

スプリントの途中でユーザーが仕様・画面・運用について判断を下したら（画面確認での指示を含む）、メインセッションはそれを **`docs/spec.md` の「ユーザー確定事項」に日付とスプリント番号付きで追記する。** 以降のエージェントはそこを読んで判断する。

- 記録するのはユーザーが明示した判断だけ。メインセッションの推測や提案を確定事項として書かない
- 既存の契約（`docs/sprints/sprint-N.md`）の内容を変える判断なら、書き換えは planner に依頼する

## 成果物とファイル配置

`docs/` は **プロジェクトルート直下の `docs/`** を指す（ファイルシステムのルートではない）。

```
pyproject.toml                   # 依存・ツール設定（ruff / mypy / pytest / coverage）を集約
.venv/                           # 仮想環境（コミットしない）
src/<パッケージ名>/
├── core/                        # ロジック層（GUI フレームワークを import しない）
├── gui/                         # GUI 層（表示と入力の受け渡しだけ）
└── __main__.py                  # エントリポイント（--smoke に対応）
tests/
├── unit/                        # generator / refiner が書くユニットテスト
└── acceptance/                  # evaluator が書く受け入れテスト（契約1条件ごと）
docs/
├── spec.md                      # planner が生成（仕様・技術スタック・重点検査・ユーザー確定事項）
├── coding-standards.md          # 任意。人間が用意するコーディング規約（置けば最優先・改変禁止）
├── sprints/
│   └── sprint-N.md              # planner が生成（計画と契約）
└── reports/
    ├── sprint-N-generator.md    # 各エージェントの完了報告
    ├── sprint-N-refiner.md
    ├── sprint-N-evaluator.md
    └── sprint-N-human-review.md # 人間の画面確認の返答
```

### 報告の保存（重要）

**各エージェントの完了報告は、受け取ったらメインセッションが `docs/reports/` に保存する。**

サブエージェントの作業ログはメインセッションのコンテキストに残らない。報告をファイル化しておかないと、次のエージェントに渡す情報も、差し戻し時の経緯も失われる。エージェントから報告が返ったら、要約せず **全文をそのまま** 保存すること。

同一スプリントで再実行した場合は上書きせず、`sprint-N-generator-2.md` のように連番を付ける。


### 次のエージェントへの引き継ぎ

エージェントを起動するときのプロンプトには、必ず以下を含める：

- 対象スプリント番号と `docs/sprints/sprint-N.md` のパス
- 直前のエージェントの完了報告のパス（`docs/reports/...`）
- 差し戻しの場合は、evaluator の不合格報告全文、または人間の画面確認の返答全文

「前のエージェントの結果を見て」では伝わらない。**パスを明示する。**

## 固定の開発環境

| 項目 | 内容 |
|---|---|
| アプリの形 | **ローカルのデスクトップ GUI アプリ。サーバーを立てない**（HTTP サーバー・ローカル Web サーバー・ブラウザで開く画面を作らない） |
| Python | **システムに入っている Python 3.10**（`python` コマンド）。`requires-python = ">=3.10"`、mypy と ruff の対象バージョンも 3.10 |
| パッケージ・環境管理 | **venv + pip。uv は使わない。** 依存とツール設定は `pyproject.toml` に集約する（実行時の依存は `[project] dependencies`、開発用は `[project.optional-dependencies] dev`）。システムの Python に直接 `pip install` しない |
| 環境の作成 | `python -m venv .venv` → `.venv/Scripts/python -m pip install -e ".[dev]"` |
| 実行 | すべて **`.venv/Scripts/python -m <モジュール>`** で行う（例: `.venv/Scripts/python -m pytest`）。venv の activate に頼らない |
| lint / format | **ruff**（`ruff check` と `ruff format`） |
| 型チェック | **mypy --strict** |
| テスト | **pytest + pytest-cov** |
| カバレッジ | **ロジック層（`core/`）で 80% 以上**。GUI 層は計測対象から外してよい |
| レイアウト | src レイアウト（`src/<パッケージ名>/`） |

技術スタックのうち GUI フレームワーク・データベース・配布方法は planner と相談して決め、`docs/spec.md` の「技術スタック」に記録する。

### 設計の必須ルール（ロジックと GUI の分離）

GUI を自動で操作しない代わりに、**画面なしで検証できる範囲を最大にする。**

- **計算・状態遷移・入力検証・ファイルの読み書き・データベース操作は `core/` に置く。** `core/` は GUI フレームワークを import しない
- **`gui/` は表示と入力の受け渡しだけを行う。** 入力値の検証や計算を `gui/` に書かない。ボタンのハンドラは `core/` の関数を呼ぶだけにする
- 画面の状態（どの項目が有効か、何を表示するか）も、可能な限り `core/` のデータ（ビューモデル）として表現し、テストできるようにする
- **エントリポイントは `--smoke` オプションに対応する。** `--smoke` を付けて起動すると、メインウィンドウを生成し、イベントループに入らずに（または即座に抜けて）終了コード 0 で終わる。evaluator はこれで「起動してすぐ落ちない」ことを確認する。ディスプレイの無い環境で必要なら、フレームワークのオフスクリーン設定（Qt なら `QT_QPA_PLATFORM=offscreen`）を使う

### テストで画面を出さない

ユーザーはテストの実行中も同じ PC で作業する。**テスト・自己テスト・評価のどれでも、ウィンドウを画面に出さず、フォーカス・キーボード・マウスを奪わない。**

- **pytest と `--smoke` は、非表示の Windows デスクトップ（`CreateDesktopW` で作るもの）の上で動かすランナー `tools/run_hidden.py` を通して実行する**（例: `.venv/Scripts/python tools/run_hidden.py -m pytest`）。透明化（`-alpha 0.0`）と画面外への配置だけでは、ウィンドウを map した時点で前面のウィンドウが替わり、フォーカスを奪うことが実測されているため。ランナーはテンプレートに同梱されている（標準ライブラリだけで動き、Windows 専用）
- それに加えて、Tk のウィンドウを作るテスト（ユニット・受け入れとも）は、ルートを作った直後に見えなくする（例: `root.attributes("-alpha", 0.0)` と `root.geometry("+-32000+-32000")`）。`focus_force()` は使わない
- キー操作の検証が見えない状態でできないときは、`invoke()` やハンドラの直接呼び出しで確かめる
- `--smoke` はイベントループに入らず、ウィンドウを表示しないまま終える
- アプリを通常起動して画面に出すことはしない（人間の画面確認を除く）

### Windows と日本語の前提

- **ファイルの読み書きは必ず `encoding="utf-8"` を明示する**（`open()`、`Path.read_text()`、`Path.write_text()`、`csv`、`json` を含む）。指定しないと Windows では cp932 になり、文字化けや `UnicodeDecodeError` が起きる
- 外部プロセスの出力を読む場合も `encoding` を明示する
- **パスは `pathlib` で扱う。** 区切り文字（`\` や `/`）を文字列で組み立てない
- **日本語・空白を含むパス**（例: `C:\Users\テスト ユーザー\書類`）で動くこと。evaluator の重点検査に必ず含める
- **GUI の和文フォントは既定任せにせず、コードで明示的に指定する。** 具体的なフォントは planner と相談して決め、`docs/spec.md` に記録する。見え方は人間の画面確認で判断する

### 既定のコーディング規約

`docs/coding-standards.md` が無い場合は、以下を規約とする（ある場合はそちらを優先する）。

- ruff の lint・format のエラーが 0 件。`# noqa` は理由をコメントで書いた場合だけ
- mypy --strict のエラーが 0 件。`# type: ignore` はエラーコード付き（`# type: ignore[xxx]`）かつ理由をコメントで書いた場合だけ
- 公開する関数・クラスに型ヒントと docstring を付ける
- 例外を握りつぶさない（`except:`、`except Exception: pass` の禁止）。ユーザーに見せるエラーメッセージは、何が起きて何をすればよいかが分かる日本語にする
- `print` によるデバッグ出力を残さない（ログは `logging` を使う）
- TODO / FIXME を残さない
- マジックナンバー・マジック文字列を散らさない（定数か設定にまとめる）

### データベース

使うかどうか・何を使うかは planner と相談して決める。ローカルアプリなので、使う場合は SQLite（標準ライブラリの `sqlite3`）か JSON ファイルを基本とする。

- DB ファイルの場所は `pathlib` で決め、リポジトリにコミットしない
- **スキーマを作った・変えたら、generator は完了報告に DDL をそのまま書く**

### 秘密情報

- 秘密情報は `.env` などに置き、**値をコード・テスト・完了報告・コミットのどこにも書かない。** 環境変数として参照するだけにする
- `.env*` をコミットしない
- メインセッションも秘密情報の値を読まない・表示しない

## 画面レベルの E2E テスト

`evaluator` は毎スプリント、`core/` 経由の受け入れテストに加えて、実際の GUI 部品をテストのコードから操作する E2E テストを `tests/acceptance/test_sprint_N_gui_e2e.py` に書く（手順は `.claude/agents/evaluator.md` の Phase 2.5）。

- Tkinter なら `invoke()`、`event_generate`、入力欄への `insert` で操作し、表示の文言・件数・描かれた文字を確かめる
- メッセージボックス・ファイルダイアログ・OS への印刷の依頼はテストの中で差し替える
- 上の「テストで画面を出さない」に従う
- アプリ側にテストのための仕掛け（ローカルサーバー、Web 版の画面、デバッグ用ポートなど）を作らない
- 見た目、本物のマウス・キーボードでの操作感、OS のダイアログそのもの、実機での印刷は、人間の画面確認で判断する

## 前提条件のチェック

パイプラインを回す前に確認し、欠けていればユーザーに伝える。

- `python --version` が 3.10 以上であること
- 使う GUI フレームワークが Tkinter の場合は `python -c "import tkinter"` が通ること
- 2スプリント目以降は `.venv/Scripts/python -m pip install -e ".[dev]"` が通ること

## やってはいけないこと

- メインセッションが実装・リファクタリングを肩代わりする
- evaluator を飛ばして「合格」とする
- evaluator の不合格を「軽微だから」と握りつぶす
- evaluator の合格前に人間の画面確認を依頼する、または人間の OK なしにスプリントを完了とする
- スプリント契約をメインセッションの判断で書き換える・緩める
- 技術スタックをユーザーに確認せずに決める
- uv を使う、システムの Python に直接 pip install する
- アプリにサーバー・Web 版の画面を作る
- `docs/coding-standards.md` を書き換える（人間の資産。変更依頼があった場合のみ）
- generator / refiner が `tests/acceptance/` を編集して合格させる
- 4エージェントを並列起動する（順序に意味がある）
- 完了報告や人間の返答を要約してファイル保存する（全文を残す）
- 秘密情報の値を読んで表示する・どこかに書く
- 実行していないテストを「通過」と書く
- ユーザーが言っていないことを `docs/spec.md` の「ユーザー確定事項」に書く
